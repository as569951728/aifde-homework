# Demo 方案

> 运行环境：`.runtime/w04/run-01/project-c`（第 9 步修订后的指标库导入，validation passed）；数据版本 qinghe-w04-v1.1；时间窗 2026-08-01～2026-09-01（完整自然月，结束日不含）。
> 三条运行全部实跑：`run-01`（主链路 A，原始提示词）、`run-02`（旁证 B，原始提示词）、`run-03`（旁证 B，同一问题、调优后提示词重跑），`query_status` 均为 `executed`，回答与查询全部有内容。

## 链路与选择理由

**主链路（A）：付费会员月报三问——"2026 年 8 月，付费会员的购买人数、销售额和复购率各是多少？"**

| 项 | 内容 |
| --- | --- |
| 服务哪项运营工作 | 沈总关心的"阶段进展怎样回应复购问题"（`materials/w03/08_业务目标与工作清单.md` 第 7 行）；本期业务目标是**应对复购下滑**（同文件第 3 行）。这条链路直接回答"8 月付费会员这一层卖了多少、多少人回头" |
| 为什么先验证它 | ①复购是本期唯一明确的业务目标，不是我们挑的题；②38 项里恰好 3 项直接对应（`monthly_paid_buyer_count`／`monthly_paid_sales_cents`／`monthly_paid_repeat_rate`），且这三项的口径**第 9 步刚按访谈证据改过**（`model_changes.md` 修订第 3、6 行）——刚改过的地方最该先验；③一次问数同时压三层边界：月末资格判定、月报范围限定、老收银未导出 |
| 为什么不是别条 | 圈选、推荐、触达动作都要先有"数对不对"这个前提；陈姐已明确线上做法不能冲击门店考核、考核口径不由她定，触达类链路现在做等于在未定口径上叠动作 |

**旁证链路（B）：三渠道结构——"2026 年 8 月，门店、小程序、商城三个渠道各自的订单数和净销售额是多少？"**

B 不是第二条 demo（`demo_annotation.json` 的 `selected_chain` 只能填一条），它是 A 的旁证：`order__channel` 是 `project-c/dimensions.json` 里现成的维度（3 值），用来验证"渠道能不能真拆"，以及回答会不会把"能拆"说成"归属已定"。

## 暂不覆盖范围与待验证条件

**这次不覆盖**：

1. **门店老收银系统的未导出消费**——据系统侧说明（老周 MSG-05318），"门店老收银系统里确实还有一部分会员的消费记录，这次没有导出""所以现在这份 CRM 订单不能当作完整的销售数据来看"。**未导出规模不可从现有数据推算，本方案不做任何估算**；两条 run 的回答末尾都已带这句限制。
2. **小程序／商城是否计入门店业绩**——陈姐（MSG-05365）"先别急着把哪一种排除掉"、小林（MSG-05376）"归属口径也不是我一个人定的"：渠道能拆，归属未定。本次只出渠道分解，不出"门店业绩"结论。
3. **卡产品范围**——正式规则文件经门店（MSG-05359）与运营（MSG-05370）两侧确认不存在，卡种范围按导出实际取值推断并标注；"在售／停售清单"无人能给。
4. **跨系统自然人**——手机号全掩码，按手机号关联的结论做不了；人数按 CRM 会员账户计。
5. **券核销**——发放与核销记录位置未取得（MSG-05378），退款>实付的成因仍待核。

**什么条件满足才能扩大**：①老收银消费导出到位且能核对其口径；②月报实际报数粒度由业务方给出（陈姐、小林两侧均"不掌握"，属终局待核）；③渠道归属口径由业务方确认；④卡产品规则文件若出现，卡种范围按文件重定。

```sh
  --question '2026年8月，付费会员的购买人数、销售额和复购率各是多少？' \
  --output artifacts/w04/demo_runs/run-01
# 旁证 B
.venv/bin/python tools/w04.py run-demo --project .runtime/w04/run-01/project-c \
  --question '2026年8月，门店、小程序、商城三个渠道各自的订单数和净销售额是多少？' \
  --output artifacts/w04/demo_runs/run-02
```

**bad case**：两条运行 `status` 均为 `ok`，**没有执行失败**——不编造失败证据。但有两处"答得对、边界没说完"，如实列为第 12 步的调优候选：

| # | 现象 | 为什么不达标 | 证据位 |
| --- | --- | --- | --- |
| 1 | `run-02` 给出三渠道分解（4,479／2,946／1,444），但**未声明"小程序／商城是否计入门店业绩"这一归属口径未定** | 陈姐最担心的正是"线上冲击门店考核"；一个渠道分解容易被直接当成门店业绩 | `run-02/.../result.json` 的 `answer` |
| 2 | `run-01` 说明了"月末符合悦享年卡、家庭季卡付费资格"，但**未说明卡产品正式规则文件未取得、卡种范围按导出实际取值** | 判定标准要求结论限定覆盖范围；卡种范围是"推的"不是"文件定的"，这层没说清 | `run-01/.../result.json` 的 `answer` |

**下一步（第 12.1，已执行）**：从两条里选了第 1 处（B 侧渠道归属），理由是它离陈姐的门店考核顾虑最近、被误用的代价最高。

- **定位**：数据与 SQL 已独立复核一致（三渠道数字与清洗后 CSV 直算逐项相同），问题不在数据层、不在工具层，落在**回答提示词／上下文**——回答里缺一条"口径未定必须声明"的约束。
- **只改一处**：`cp product/w03_answer_prompt.txt customer/w04/answer_prompt.txt`，在第二段"只说明实际应用的筛选和分组"之后插入一句 47 字（"按渠道分组时，要说清这是按成交渠道的分解，不等于门店业绩归属，渠道归属口径未经业务方确认时必须写明待确认"），其余逐字未动（diff 核对：仅此一处插入）。
- **同问题重跑**：问题串从 `run-02/.../result.json` 的 `question` 原样取出，一字不差；`--answer-prompt customer/w04/answer_prompt.txt`，输出 `run-03`。
- **结果**：回答新增"按成交渠道分解不等于门店业绩归属、渠道归属口径需业务方确认"，**三个渠道数字（4,479／2,946／1,444）与净额（758,163.74 元）一字未变**——说明改善只来自提示词这一处，没有动数据口径。
- **同问题下仍存在的一处未调**（如实记录，不加 tuning）：`run-01`（A 侧）没有声明"卡产品规则文件未取得、卡种范围按导出实际取值"。本轮每步只改一处，故未动；处理方向同上，属同类提示词缺口。

## 判断说明：关键假设及继续、缩小范围、调整方向的条件

**关键假设**（每条都能被证伪）：

1. "付费会员"＝**月末**持有悦享年卡／家庭季卡、且当月有有效订单的会员账户（不是任意时点持有、也不是全部在售卡种）；
2. 销售额＝已支付订单实付 − 累计退款，取消单不计；全额退款单净额为零但仍属已支付集合；
3. 复购＝月内有效订单 ≥ 2 笔，分母是当月付费购买人数（493）；
4. 渠道三值是**成交渠道**，不等于业绩归属；
5. 8 月是完整自然月，可作为口径验证窗口（数据到 2026-09-01 不含）。

**最小验证链路的选择依据**：只用一个问题压住三层边界（资格判定＋范围限定＋来源缺口），比铺三条各压一层的链路更省，也更容易判断"是口径错还是模型错"——数字对得上、SQL 也读得懂，剩下的问题就只可能在回答措辞。

**继续的条件**（具体到能判断）：8 月三问的数字能被业务方与月报实物对上（哪怕只是量级），且同一口径换月份（如 2026-07）仍返回同结构答案、复购率不出现跳变式异常。

**缩小范围的条件**：若业务方指出月报实际是分渠道或分门店各报一栏，则本链路的"全渠道合计"降为其中一栏，先只做合计口径并在回答中标注"颗粒度待定"，不再出任何单渠道结论。

**调整方向的条件**：①若老收银未导出消费被业务方确认为不可忽略（给出判定阈值），则一切"总量／全量"类问法改口径或改问法，demo 结论随之作废重跑；②若后续拿到卡产品规则文件且卡种范围与导出实际值不符，则 `monthly_paid_*` 三项需按文件重定，历史回答标注失效。
