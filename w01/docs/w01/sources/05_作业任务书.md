# W1 作业任务书：接手标准产品，判断是否继续

> 任务版本：`w01-task-0.2.1`，2026-09-12。对应材料 `w01-materials-0.2.4`、官方产品 `0.2.0-w1`。fit-gap 契约为 `w01-0.2.1`，其余三份 JSON 沿用 `w01-0.2.0`。访谈入口和截止时间按班期配置。

## 一、本周任务与投入

材料清单与阅读顺序见同目录的[使用说明](00_使用说明.md)。本任务书统一说明要做什么、提交什么，以及如何判定和补齐。

你是标准 Agent 产品的 FDE。根据沈总邮件、公司与协作说明、产品能力和首轮访谈，提出是否进入下一阶段的判断。目标是让证据足以支持下一步行动，不是提前承诺完整功能或效果数字。

本周先运行标准产品并完成真实模型、业务工具、数据与标签 API 验证，保存模型基线，再形成 fit-gap 和立项分析。复用官方产品的学员不开发青禾业务功能；自建路线需另外实现等价标准能力。两条路线按相同数据、API、行为和产出物验收。

本周不提供标准 fit-gap 或立项报告答案，也不发青禾清洗、身份合并或客户连接器答案。已有标准产品仍需在后续各周完成客户适配与调优。

本周投入以完整任务为准，不沿用原 1–2 小时或 2–3 小时的估计。记录安装、运行、诊断、模型适配、文档和回归分别花了多久；自建底座额外投入单列。环境故障应留下脱敏证据，不手改检查结果赶进度。

W1 只可约沈总。先写目的，正式访谈按每周每角色最多 2 次预扣，系统失败返还，主动结束不返还。使用真实访谈记录形成判断，不能将固定回放当成已完成访谈；正式入口尚未开放时，先完成独立的工程准备，访谈与交付门槛留待补齐。

### W01 的 fit-gap 要做到什么程度

本周提交 **fit-gap 初步版**。依据有两类：沈总邮件、首轮访谈和公开客户材料，说明客户诉求及当前说法；同版产品能力矩阵、代码和自己的运行记录，说明标准产品已经验证了什么。学员经过整周学习、运行与访谈后，再整理本周判断。

W01 只开放沈总。其他角色的实际工作流程、客户数据质量、指标口径和系统接入条件尚不完整，可以保留未知或冲突。每条诉求写清目前能判断到哪里、依据是什么、还缺什么，以及下一步找谁取得什么证据、结果会改变哪个判断。标准样例成功不能写成青禾已经适配；沈总的单方说法不能直接写成已核实事实。

分类有部分依据时，可以保留初步分类并据实标记证据状态；连初步分类都无法支持时，选择“待判断”。“待判断”表示尚不能确定适配方式，“暂不承诺”表示当前不作相应交付或效果承诺，两者含义不同。“待判断”是分类尚未形成的占位，不新增一种实施工作。能力 ID 或证据尚无依据时可以留空，下一步必须具体；已有证据的状态仍按其实际支持程度填写。

本周不按“填满多少行”“消除多少未知”评分，也不要求五种处理分类各出现一次。合理保留待判断并给出核实路径可以达标；已有公开材料或本周可取得的产品验证依据，却一律写未知、待判断或“继续调研”，仍需补齐。四问提纲帮助组织立项报告，fit-gap 保存适配明细，两者不新增必交文件。

## 二、产出物契约

解压材料中的工程包，在自己的客户交付工作目录中保留以下文件。后续各周继续使用这个仓库。

| 固定路径 | 必填内容与上游依据 | 检查方式 |
| --- | --- | --- |
| `artifacts/w01/environment_check.json` | 契约与产品版本、检查时间、实现路线、运行时、模型模式及 9 项检查状态 | 工程包 `contracts/w01/environment_check.schema.json`；公开预检与运行抽查 |
| `artifacts/w01/product_fit_gap.json` | 版本、能力矩阵版本、逐项请求、初步分类或待判断、能力 ID、证据状态、依据位置和下一步 | 工程包 `contracts/w01/product_fit_gap.schema.json`；公开预检加人工判读 |
| `artifacts/w01/model_baseline.json` | 实际模型与协议、提示词哈希、数据版本、至少 4 次场景运行、失败分类与下一步 | schema 与真实运行复核 |
| `artifacts/w01/runtime_evidence.json` | 7 类行为结果、证据文件路径及 SHA-256、实现路线与限制 | schema、哈希校验、API 与 Agent 行为抽查 |
| `docs/w01/project_assessment.md` | 业务问题与诉求拆解、当前事实与角色转述、适配判断、风险和待核项、下一阶段建议及承诺边界 | 非空与路径检查；内容由助教判读 |

JSON Schema 是字段定义的唯一工程来源，不根据本表自行增加字段。fit-gap 的 `contract_version` 为 `w01-0.2.1`，其余三份 JSON 为 `w01-0.2.0`；能力矩阵版本仍为 `w1-capabilities-0.2.0`。其他栈或等价底座填写自己的真实 `product_version`，四个 JSON 中保持一致。新版 fit-gap 契约兼容原 `w01-0.2.0` 的五类作业；使用“待判断”须采用 `w01-0.2.1`。

环境检查的 9 项为 `runtime`、`database`、`tool_registry`、`product`、`model_api`、`checker`、`label_api`、`evaluation`、`trace`。状态可为 `pass / fail / skipped`，完整技术就绪要求全部 `pass` 且模型模式为 `live`。这些是实际运行的记录，不是勾选声明。非 Python 路线还需能运行官方 Python checker，运行证据可写在报告工程备注中，不新增 schema 字段。

fit-gap 的 `category` 可取“产品已有、客户配置、系统适配、产品缺口、暂不承诺”，依据不足以分类时取“待判断”。`evidence_status` 分别取 `verified`、`reported`、`unknown`、`conflicting`，对应已核实、角色转述、未知、冲突。分类与证据状态分别填写；选择某个分类不会让证据自动变成已核实。证据用 `source` 标来源、`locator` 标段落或消息位置、`note` 写这份依据支持什么。单一角色的口头判断不能仅因表达明确就记为 `verified`。

可以暂时没有足够证据，但必须说明下一步怎样补；分类按实际内容填写，不要求五类各凑一条。报告不规定字数，用足够清楚的证据支持结论即可。不要附密钥、真实客户数据或供应商的完整认证配置。

## 三、从领取到提交

1. 解压材料包内的 [标准产品 0.2.0 工程包](工程/fde-student-w01-0.2.0.zip)，按 ZIP 内的 README 安装依赖；执行 `tools/product.py init` 导入干净样例，执行 `tools/check_product.py --dry-run` 校验契约。产品支持 fit-gap 契约、多轮会话、日期确认、拒绝草案和退款说明。保留自己的代码、模型配置、数据和运行记录；修改代码后需重启产品服务。
2. 配置自己选择的模型。启动独立标签服务与产品网页，先完成明确时段的分析，再测试缺参数澄清、部分覆盖和只读拒绝。网页上查看工具依据，不能只看最终一句回答。
3. 打开样例动作模式，检查草案、明确确认、HTTP 执行、查询与撤销。修改目标必须重新确认，重复请求不能重复生效。用 API 文档核对真实服务状态，不直接写动作表。
4. 官方路线执行 `tools/verify_product.py --live` 生成模型与运行证据，按 `evals/README.md` 运行 Promptfoo；评估完成后用 `tools/finalize_evaluation.py` 读取实际报告补齐环境状态。不同模型的接口不兼容时修改适配器并保留证据，不使用教师验证结果代替本机结果。
5. 根据材料、产品能力及访谈记录，按下方“fit-gap 填在哪里”完成填写和转换，再完成立项报告。W1 调优记录允许是基线、失败归因和后续假设，不要求声称已经获得效果提升；需要改协议或配置的，提交实际改动与验证。
6. 执行 `tools/check_product.py --root .`，修正具体字段或证据问题。提交四份 JSON、立项报告及所引用的证据文件，保持路径；提交源码与依赖说明供抽查，排除密钥、`.venv` 和无关内容。

模型由你选择，不限定厂商。官方适配器可配置兼容接口，其他协议可以替换适配器。安装依赖、模型调用均在本地完成；真实调用产生的费用按所选服务计费，密钥不进入作业。离线回放只能帮助读代码和诊断，不能证明真实模型已经接入。

所有 Python 脚本使用安装包虚拟环境运行。Windows 路径按 ZIP 内的 README 调整。自主路线可以使用不同内部结构，但必须输出同一契约，并接受现场重跑。数据缺失且无法形成名单时，明确返回未完成与依据属于正确处理，不能为追求 completed 编造结果。

预检通过不等于最终成绩。checker 不能证明作者身份、建议价值、所有语言判断的真实性或客户承诺是否合理，这些由运行复核与 rubric 判断。

### fit-gap 填在哪里

材料包提供 [fit-gap 空白表](06_fit-gap空白表.xlsx)和[转换工具](07_fit_gap_to_json.py)。在 Excel 或能保存 `.xlsx` 的表格软件中填写，再转换成第二节规定的 `artifacts/w01/product_fit_gap.json`。

1. **准备填写稿**：将空白表另存到解压后的工程目录，路径为 `artifacts/w01/product_fit_gap.xlsx`；将转换工具复制到同一工程的 `tools/07_fit_gap_to_json.py`。原空白表留作备用。
2. **填写两张表**：“适配判断”每个诉求一行，编号从 `GAP-001` 开始，保持唯一；选择适配分类和证据状态，填写客户诉求、能力 ID 与下一步。“证据明细”每份证据一行，用同一编号关联诉求，写明来源、定位和支持内容。同一诉求可以对应多份证据。没有能力依据或证据时相应位置留空，状态据实填写，不用“无”代替空值；下一步仍须写清。每份表最多 100 条诉求，每条最多 20 份证据，均沿用现有契约。
3. **保存并转换**：保留工作表名称、第 4 行版本区与第 9 行表头，填写实际值，不使用公式。产品版本按自己的实现填写，其余版本保持。保存填写稿后，从工程根目录运行以下命令。

macOS／Linux：

```sh
.venv/bin/python tools/07_fit_gap_to_json.py
```

Windows：

```powershell
.venv\Scripts\python.exe tools\07_fit_gap_to_json.py
```

工具默认读取 `artifacts/w01/product_fit_gap.xlsx`，生成同目录的 `product_fit_gap.json`，沿用工程已安装的 `jsonschema` 依赖，无需额外安装 Excel 读取库。空表、必填项缺失、编号重复、无效分类、未知能力 ID、证据编号不对应，以及“已核实但无证据”都会阻止生成，并提示问题位置。已有 JSON 默认不覆盖；确认要用本次填写更新时，在转换命令末尾加 `--overwrite`。

转换成功只说明格式和引用检查通过。还需完成其余产出物，再执行本节第 6 步的公开预检；证据是否充分、判断是否合理，由助教复核。Excel 是个人填写稿，不新增必交文件，正式提交仍使用第二节的 JSON 契约。自建路线可以借助官方工程目录的契约与能力矩阵完成转换，再将生成的 JSON 放入自己的交付目录；表中的产品版本必须填写自己的实际版本。

### 提交以后，怎样继续修订 fit-gap

W01 提交版保留在 `artifacts/w01/`，作为当时证据和判断的记录。后续继续使用同一个客户仓库和条目编号，有新证据或范围变化时更新相关条目。

| 阶段 | 需要补充或修订的内容 |
| --- | --- |
| W02 | 用多角色访谈核实工作流程、技术条件与角色分歧，修正初步分类，保留未解决冲突 |
| W03 | 结合指标定义和 SOW，明确本期范围、延后事项、责任与承诺边界 |
| W04–W05 | 用实际数据和客户 MVP 验证，确认哪些差异由配置、系统适配或产品扩展处理 |
| 后续范围变化时 | 对受影响的条目重新核查，例如 W07–W08 新增的执行诉求；无需每周重填整表 |

从 W02 开始，将上一版填写稿另存为 `artifacts/w02/product_fit_gap.xlsx`，沿用 `GAP-001` 等编号，只新增或修改有变化的条目。在当周已有的访谈纪要、SOW 或交付报告中，用“适配判断更新”小节记录条目编号、原判断与新判断、变更原因和证据位置。未解决事项保留，不为清空待判断而强行下结论。

在工程根目录运行转换命令，并在末尾增加 `--week w02`，生成 `artifacts/w02/product_fit_gap.json`；以后将 `w02` 换成对应周次。已有当周 JSON 需要更新时，再加 `--overwrite`。例如 macOS／Linux：

```sh
.venv/bin/python tools/07_fit_gap_to_json.py --week w02
```

Windows 使用前文的 Python 路径，参数相同。指定后续周次不会覆盖 W01 文件；不要只改输入路径而遗漏 `--week`。当前转换沿用 fit-gap `w01-0.2.1` 数据格式，后续若发布新契约，以当周任务书为准。

后续修订用于支持当周已有作业，不新增一项每周独立提交任务；是否随包提交以当周任务书为准。W01 截止前修改可以更新当前文件；截止后如需补齐，先保留已提交版本，再按助教反馈提交修订版。

## 四、双门槛与补齐

技术门槛看产品运行、真实模型与工具闭环、契约完整，以及 fit-gap 是否有能力依据。交付门槛看能否区分诉求与事实、提出必要核查对象，并在不确定性尚存时守住承诺边界。两项分别判定，不以写代码多、文档长或表达流畅抵消另一项缺失。

未达标不阻断后续材料解锁。助教反馈应列具体缺项和补齐方式，核心项在答辩前补齐。环境卡住时提供操作系统、运行时版本、命令、脱敏错误码和已尝试的方法；不把供应商故障算成学员沟通失败。

W1 checkpoint 在作业截止后的复盘发放，随报随学按个人截止时间解锁，不以月度复盘完成为前提。只提供产品基线、自检样例和能力矩阵，不提供标准 fit-gap 或立项报告答案。另解压到参考目录比较或按说明接续，不覆盖自己的修改；引用了哪些参考资产，在报告中据实说明。
