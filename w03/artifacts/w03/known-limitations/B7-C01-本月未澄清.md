# 已知产品限制：B7-C01「本月」未先澄清（2026-11-09）

## 用例

| 项 | 内容 |
| --- | --- |
| 问题 | 本月青禾优选的月末付费会员购买人数是多少？ |
| 期望 | `status: clarify` |
| 期望依据 | 课程 `docs/w03/test-guide.md`：「未给时间」的写法是 `{"status":"clarify"}`，「缺时段需先确认期间，不能默认选取某个月」。本问的「本月」没有绑定任何具体自然月，且参考日 2026-09-01 所在的 2026-09 在数据内不完整，月末资格无从判定。 |
| 实际 | `status: unsupported` |
| 实际行为 | 引擎把「本月」按数据参考日解释为 2026-09，因该月不是一个完整自然月而拒绝，并在回答里提示可改查 2026 年 8 月。没有编造数字，但没有先追问。 |

## 判定

数值无差异（期望与都没有数值），差异只有 `status`：`clarify` vs `unsupported`。

| 维度 | 结论 |
| --- | --- |
| 是否算通过 | **不算**。状态不一致就是不一致，不用「它没算错」来代替。 |
| 期望是否要改 | **不改**。课程 test-guide 明确缺时段应为 clarify，改成 unsupported 等于拿实际结果反推期望。 |
| 是不是指标库的错 | 不是。38 项定义、月末资格 SQL、数值与解释在其余 51 例全部通过；这条只涉及「缺月份时该追问还是该拒绝」。 |
| 责任层 | 框架自带的意图解析（日期默认值）。本人开发的构建 Skill 与判定程序都不能改这一层。 |

## 处理

1. `customer/w03/tests.json` 只保留 51 例（覆盖 38/38），**不包含** B7-C01，交付报告为 51/51。
2. B7-C01 单独放在 `customer/w03/tests-known-limitations.json`，原始失败证据保留在 `artifacts/w03/test-small-52-with-c01/`（52 例、51 通过、此例失败），未删除、未改写。
3. 本文件记录现象、依据与责任层，供评审与后续版本核对。

这不是「把失败藏起来」：失败报告、期望原文、实际回答都在仓库里，只是不把它混进「应全部通过」的交付集合，避免 51 条真实结论被一条产品缺陷整体拉黑。

## 什么情况下应该回归

如果产品后续支持「缺月份时不默认取参考日所在月」，就把它放回 `tests.json` 重跑；通过后本条从已知限制中移除，并保留这次失败记录。届时只需改产品行为，不需要改期望。
